# 0012 — Registration session response contract

- **Status:** Accepted — implementation pending
- **Decision date:** 2026-09-22
- **Ticket:** TICKET 12 — Product decision: `UserCreatedResponse` never populates `token`/`expiresIn`/`refreshToken`
- **Scope:** Documentation and decision record only. No runtime behavior is changed by this ticket.

## Context

Today `POST /auth/register` already produces a MyVanitys JWT, but the API discards it before responding:

- `RegisterUser` exchanges the Google authorization code, creates and saves the user, builds `TokenClaims`, generates the MyVanitys JWT, and returns `new UserRegistrationResult(new UserSession(token, newUser))`. The use case therefore already yields a usable MyVanitys access token.
- `AuthController.createUser` throws that session away by calling `createUserMapper.toResponse(result.session().user())`.
- `CreateUserMapper.toResponse(User)` maps only `user.id.value` into `userId` and explicitly ignores `token`, `expiresIn`, and `refreshToken`.
- `CreateUserMapperTest.when_validUser_then_returnsResponse` locks the current behavior in by asserting the three credential fields are `null`.
- The published schema (`UserCreatedResponse`) still advertises `token`, `expiresIn`, and `refreshToken` even though they are never populated.
- The web client deliberately forces a second Google OAuth/login flow as a workaround: `registerService.js` sets `requiresLogin: true` and `AuthCallbackHandler` routes the user back through the login flow.
- Current documentation (`doc/API_OVERVIEW.md` and `doc/sequenceDiagrams/googleAuthNewUser.mermaid`) accurately describes this deployed behavior, but describing deployed behavior is not evidence that the behavior was ever an intentional product design.
- Commit history shows the original response implementation was marked temporary: `3f4219f` (`VANITYS16: Implement user registration functionality and related exceptions`) added `createUser` returning `ResponseEntity.status(HttpStatus.CREATED).build(); // temporal`.

Because a Google authorization code is single-use, the second login call cannot safely re-exchange the original registration code; the client must start a fresh Google OAuth authorization flow. That extra round trip is the source of the onboarding friction this decision removes.

This is classified as technical debt, not an intentional two-step product contract.

## Decision

Registration and the user's initial authentication become a single operation from the client's perspective.

A successful registration response returns exactly:

- `userId`
- `token`
- `expiresIn`

Where:

- `token` is the MyVanitys JWT already generated by `RegisterUser` (via `TokenClaims` + `TokenGenerator`). It is not a Google credential.
- `expiresIn` is the exact number of seconds between the JWT claims' `issuedAt` and `expiresAt` (`Duration.between(issuedAt, expiresAt).toSeconds()`), derived from the same `TokenClaims` used to sign the returned token.
- `refreshToken` is removed from the registration schema. It will only be reintroduced when MyVanitys implements a complete refresh-token feature (issuance, persistence/hashing, rotation, revocation, expiry, replay handling, and a documented refresh endpoint).

The client uses the returned access token immediately and does not perform a second Google OAuth/login flow after a successful registration.

## Security constraints

- Never return a Google access token or a Google refresh token as the MyVanitys authentication token.
- Never expose `GoogleTokenResponse.refreshToken`. It is an upstream Google credential, not a MyVanitys credential.
- Never use the access JWT itself as a refresh token.
- Never fabricate a placeholder or dummy refresh token, and never advertise null-filled fields as functional credentials.
- Refresh-token support requires dedicated issuance, hashing or secure persistence as appropriate, rotation, revocation, expiry, replay handling, and a documented refresh endpoint.
- `token` and `expiresIn` mapping must originate from the same `TokenClaims` instance used to sign the returned JWT. `expiresIn` must not be obtained from a hard-coded or environment-duplicated value, and must not be recovered by reparsing the token.

## Coordinated implementation plan

The change spans three repositories plus deployment. The rollout must be **backend-first**. A contract-first order is **not** backward-compatible: publishing a schema that makes `token`/`expiresIn` required before production populates them would break any client that generates code or validates responses against the contract. The order below is the backward-compatible one.

### Phase 1 — API contract prepared, not published (`myvanitys-api-spec`)

- Prepare a dedicated branch in `myvanitys-api-spec` (do not work on `main`).
- Update `UserCreatedResponse`:
  - Make `userId`, `token`, and `expiresIn` required.
  - Remove `refreshToken`.
- Generate and test the models on that branch.
- **Do not version, publish, or promote the new artifact yet.** The stricter schema stays off the published channel until the compatible backend is deployed (Phase 3).
- Do not edit generated Java sources manually; they are produced from the spec.

### Phase 2 — backend implements against the current published model (`myvanitys-api`)

- First implement and deploy `token`/`expiresIn` using the **current `1.11.0-SNAPSHOT` model**, whose `UserCreatedResponse` already declares both fields as optional. No dependency bump is required for this step.
- Preserve `TokenClaims` information through `UserRegistrationResult` (currently the session carries only `token` and `User`; `issuedAt`/`expiresAt` are not propagated to the response layer).
- Map the whole registration result/session instead of mapping only `User`.
- Return the existing MyVanitys JWT.
- Calculate expiry from the exact claims (`issuedAt`/`expiresAt`), not from configuration duplication and not by reparsing the JWT.
- Leave `refreshToken` unpopulated; the optional field simply stays absent in this transitional release.
- Add mapper, use-case, controller, and HTTP-contract tests.
- Resolve the existing registration `200` vs OpenAPI `201` mismatch in a separately authorized ticket, not incidentally in this one.
- Deploy this compatible backend before the schema is strengthened. Existing clients keep working because the extra fields are additive and optional under the current contract.

### Phase 3 — publish the stricter contract, then converge the backend

- After the compatible backend from Phase 2 is deployed, version and publish/promote the new specification artifact (e.g. a new `1.x` snapshot/release under GitHub Packages) with `userId`/`token`/`expiresIn` required and `refreshToken` removed.
- As part of this same coordinated contract update, bump the backend's API spec dependency to the newly published artifact.
- Remove the now-obsolete `refreshToken` mapping declarations (the `@Mapping(target = "refreshToken", ignore = true)` in `CreateUserMapper` and the corresponding mapper test assertions) since the field no longer exists in the generated model.
- Verify the backend still compiles and its tests pass against the stricter model.

### Phase 4 — web (`myvanitys-web`)

- Consume `token` and `expiresIn` from the registration response.
- Set the authenticated state immediately after registration.
- Remove `requiresLogin: true`.
- Remove the second Google OAuth/login flow after successful registration.
- Preserve the existing `409` already-registered behavior and its UI route to login.

### Phase 5 — documentation and sequence diagrams

- Update API consumer documentation (`doc/API_OVERVIEW.md`) and the registration sequence diagram (`doc/sequenceDiagrams/googleAuthNewUser.mermaid`) only after the runtime behavior is actually deployed.
- Confirm older clients still tolerate the additional populated fields during the transition.

## Consequences and rejected alternatives

Accepted consequences:

- Better onboarding experience with one fewer Google authorization round trip.
- No redundant second Google authorization.
- The JWT already generated by the backend is no longer discarded.
- The response contract describes actual behavior instead of advertising unused fields.

Rejected alternatives:

- Keeping the two-step registration/login flow as the permanent product design.
- Returning only `userId` and never a token.
- Returning `null` fields that are advertised as functional credentials.
- Returning Google access or refresh credentials to the client.
- Reusing the access JWT as a refresh token.
- Implementing a refresh token without a refresh endpoint and lifecycle.
- Editing the locally checked-out `1.7.0-SNAPSHOT` schema as though it were the published `1.11.0-SNAPSHOT` dependency.

## Current-state warning

- This decision is **not implemented** by TICKET 12. TICKET 12 records the decision and the rollout design only.
- The deployed/current API still returns only `userId`; `token`, `expiresIn`, and `refreshToken` are not populated.
- Clients must continue using the existing two-step behavior (register, then call `POST /auth/google`) until the coordinated rollout is complete.
- Nothing in this record should be read as claiming that token-bearing registration is already available.
